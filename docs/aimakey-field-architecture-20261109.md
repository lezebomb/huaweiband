# AimaKey：从手环发起、手机离线记录的开发路线

2026-11-09。本轮修正验收方法：不再要求用户到车旁重复演示已说明的官方 App 流程；系统验收必须最终覆盖“手环发起 → 锁屏手机 → 车辆实际状态 → 手环反馈”。日志随手机离线记录，回家后再导出，不要求骑车时带电脑。

## 已知事实与不能由此推出的结论

**用户真机观察，2026-11-09补充**：未启动时，官方控件显示“右滑启动”，蓝牙连接后右上角显示“蓝牙已连接”；启动后控件变为完整图标，点按同一控件即可正常关闭；手机锁屏时官方 App 可维持车辆连接。

这些事实已作为需求输入接受，不再让用户重复证明 UI 存在。它们不能证明其他 Android 应用能直接调用官方 App 的内存对象、Flutter MethodChannel 或蓝牙连接，也不能把UI“已连接”当成第三方取得了新鲜电源／静止状态。[Android应用沙箱](https://developer.android.com/privacy-and-security/security-tips)隔离其他应用的代码与私有数据。

官方控件会切换语义，因此生产接口必须表达目标状态：START只要求开启，STOP只要求关闭。不能实现成无条件点同一个图标。本轮增加：电源状态未知时拒绝；已处于请求目标状态时返回“当前状态已符合，未发送新动作”；停止仍需明确确认和新鲜静止证据。只有真实适配器取得这些状态，才允许替换Mock。

## 最终结构与本轮实际实现

```text
最终：独立手环页面（常驻入口仍待证实）
 → 经过身份校验的手环命令
 → 手机协调器（串行、去重、目标电源状态、停止门控）
 → 已授权且可由第三方使用的爱玛适配器（仍缺）
 → 车辆状态确认 → 手环反馈
 └→ 手机私有目录事件记录 → 用户稍后导出ZIP

本轮临时诊断：手机手动请求一条120秒通知
 → 真实手环“启动测试／关闭测试”
 → Wear Engine真实按钮回调
 → 手机记录点击及当时锁屏状态
 → 尝试返回“手机已收到，未控制车辆”的无按钮通知
```

用户本轮明确接受一次性通知用于临时手环通信诊断，并保留最终常驻页面目标。该通知不会自动续发；一条只接受一个按钮动作，过期、取消、重复及旧回调不再接受。它不是可随时主动打开的独立App页面，不作为最终交付降级方案。

## 复用原BandKey授权，隔离诊断实现

华为[官方FAQ](https://developer.huawei.com/consumer/cn/doc/connectivity-Guides/faq-0000001050818031/)要求App ID、包名、签名与服务配置一致。上阶段独立包`dev.bandkey.aimakey`不能复制原App ID就当成获得授权。

本轮在原授权包`dev.bandkey.bridge`增加`AimaWearFieldActivity`和`AimaWearFieldService`，都运行在`:aimakey`进程。诊断代码不调用PC客户端、身份签名、Windows grant或车辆适配器。新增通知channel和记录目录独立，原主桥接只增加导航。更新包使用原本机签名，证书与0.9.5回滚APK比对一致，保留应用数据，不卸载重装。

同一授权包仍可能共用穿戴通知通道，因此诊断在原Windows手机桥接／传输服务运行时拒绝发通知，需要用户在原设置中手动暂停，测试后手动恢复。不会自动暂停、恢复、审批或签署Windows请求。独立进程不等于设备通知通道天然隔离，这项限制明确保留。

独立AimaKey 0.2.0继续提供手机Mock、打开原包的手环诊断、查看和导出本包记录。它未接入真实车辆。

## 无电脑的诊断记录

新增`:aimakey-field`共用Android模块和核心`FieldTraceStore`：

- 保存本应用手机动作、真实手环回调、SDK接受／失败、处理阶段、墙钟和单调时钟、当时亮屏／锁屏／省电状态。
- 事件为固定枚举和数值字段，没有自由请求内容、设备UUID、车辆标识、蓝牙密钥、账号凭据或Windows签名材料。
- 手环来源用`WRIST_NOTIFICATION_TEST`和`WRIST_GESTURE`标明；`vehicleSimulation=true`及`realVehicleAdapter=false`说明车辆仍未接入，与点击是否来自真实手环是两个维度。SDK接受通知和真实手环点击分别记录。
- 每个文件最多128 KiB，保留8个文件；到上限记录截断标记，不无限增长。重启后仍可读；时钟回拨不误选旧文件；不完整尾行导出时排除并注明。
- 收到手环点击后，在记录写入队列完成后才结束前台诊断；写入失败显示失败，不把缺失记录解释成没有动作。
- 手机点“查看／导出本机记录”，通过系统选择保存位置；ZIP只包含这些事件，不自动上传。两个包各自导出各自的记录。

本应用没有READ_LOGS权限，不保证读取官方App的私有日志。[READ_LOGS](https://developer.android.com/reference/android/Manifest.permission#READ_LOGS)不是普通第三方应用通用可用的能力。后续主要依赖我们自己的命令和适配器状态记录定位问题；如果确需官方原始日志，再研究用户发起的官方导出途径，不把电脑连接作为路测前提。

## 构建、验证与边界

- AimaKey核心58项通过；本地文件恢复、容量、导出、单次消费和过期策略33项通过。
- 两个App、共用库和instrumentation构建通过，Lint均零错误。原BandKey保留6项原有警告，AimaKey／共用库各1项文本国际化警告。
- 原BandKey Java151项回归通过。Windows源码、原生登录组件和PC授权协议未修改；未将软件回归冒充完整真机Windows解锁验收。
- 真机自动化与真实手环人工回调分别记录，不将Mock或人为注入SDK回调计作真实手环通过。

本轮随后完成的真机证据：

| 验证 | 实际结果 | 边界 |
|---|---|---|
| 手机Mock与离线记录instrumentation | 17项通过，`keyguardLocked=true`、`screenOffTest=true` | 包括持久读取和手机内生成ZIP；不是实车 |
| 原桥接占用检查 | 记录`HOST_BUSY`并拒绝发送诊断通知 | 用户之后手动暂停了原桥接 |
| 用户在11 Pro点“启动测试” | SDK真实`WRIST_GESTURE START`，code=2 | 当时手机亮屏、未锁，不能作为锁屏证据 |
| 用户先锁手机，再在11 Pro点“关闭测试” | SDK真实`WRIST_GESTURE STOP`，code=3，screenFlags=6 | 6=熄屏、Keyguard锁定、电池优化豁免；未控制车辆 |
| 返回手环收件通知 | 两次都有SDK接受记录，code=2 | 未独立采集手环屏幕，不把SDK接受冒充用户看到回执 |
| 本地保存 | STOP事件、返回SDK接受和服务结束均在手机私有文件中，随后只读回取核实 | 电脑用于事后读取，未参与点击接收或记录 |

因此本轮可以声称“真实手环点击→锁屏手机接收→手机离线保存”通过。没有声称已实现常驻页面、已发送车辆指令或已验证长期Doze和实车启停。

`scripts/package-aimakey-field.ps1`要求原签名文件和仅本进程密码环境变量，不把私钥拷入输出。产物和同签名0.9.5回滚包位于忽略目录`artifacts/aimakey-field/`。手机步骤和回滚见[测试指南](aimakey-real-vehicle-test.md)。

下一阶段先解决两个关口：11 Pro可安装／可常驻的第三方入口，以及可合法复用的爱玛控制与状态API。本轮没有发现新接口证据，没有重放认证、注入或盲点UI。两个关口未证实前，不能承诺当前硬件已能完成最终产品目标。
