# BLE 轮询恢复修正（2026-10-23）

## 本阶段修正

Android 0.3.2 修正 VM 实验页的连接恢复流程。若使用本页或后台服务启动的 BLE，GATT 尚未连接／订阅时先显示等待，不向尚不可用的本地 TCP 入口发起 TLS 握手。GATT 恢复只允许重新尝试；只有 HTTPS 轮询成功后才显示电脑 TLS 身份已核验。USB 及没有由本应用启动 BLE 的网络通道继续使用原有轮询方式。

原页面在成功轮询返回“没有新请求”时不更新状态，因此启动或断线时的 `SSLHandshakeException` 可能一直留在页面。现在实际恢复后清除过时的错误提示；这不将尚未成功的请求标记为正常，也不改变电脑助手的历史故障记录。

轮询失败使用原有单调时钟退避，延迟从 4 秒增加到最多 60 秒。BLE 断开时暂停网络尝试，重连后可以立即尝试新的轮询。此状态只负责查询可用性，不保存授权，不重复发送确认／拒绝，不延长票据或原生挑战的有效期；停止／离开页面仍取消原请求。

手机流处理保留下载线程的首个错误，避免关闭本地 Socket 后只看到次生 `Socket closed`。最后一条原因链保存在应用私有文件 `vm-ble-stream-error.json`，最多 8 层、每层原因最多 256 字符，未导出或上传。证书固定、电脑签名、一次性授权与前台确认限制保持不变。

## 证据与限制

修正前，VM 唤醒后分别连续完成 35 条和 29 条真实 BLE 流，均未发生重连或传输失败；旧助手的 PDB 源文件校验值与仓库版本相符。它们是有限观察，不能证明此前的 `target-read / 10053` 已被修复。

0.3.2 已保留数据安装到一加，使用同一 VM 中继、同一证书和原实验密钥，USB 无授权数据映射。本阶段不调用手环按钮或批准 Windows 解锁。

| 检查 | 结果 |
|---|---|
| 手机先启动 BLE 和轮询，电脑尚未连接 | 实际显示等待 BLE，没有把 GATT 就绪当作 TLS 身份验证 |
| 再连接电脑助手 | 自动显示通信正常、电脑 TLS 身份已核验，完成 11 条流，1 次连接、无传输故障 |
| 主动停止电脑助手 | 手机自动回到等待 BLE，未再次点击手机启动按钮 |
| 再次连接电脑助手 | 未点击手机启动按钮，实际恢复到已核验证书的轮询；累计完成 24 条流，随后在 86.238 秒记录 1 次 `gatt-write-timeout`，不标记全程稳定 |

Android 构建、APK 签名校验及 Lint 通过（0 错误、4 警告）。Java 检查共 71 项通过，其中新增 3 项验证等待 GATT、退避及恢复顺序、恢复不能复活过期／已消费授权。Windows 代码最终没有改动，未重复执行旧的整套原生及 Windows 登录测试。

此前真实手环 USB／BLE 解锁结果继续见 [手环联调记录](wearengine-validation-20261023.md)。本阶段验证连接恢复，不作为新版手环解锁或 BLE 拒绝交付的验收。

仍待定位：此前间歇性的直接 BLE `target-read / 10053`，以及本次重连后的 GATT 写入超时。超时在助手停止前已发生，不能归因为正常收尾，也不能仅凭一部分流成功就关闭问题。新增首个错误记录用于下一次发生时区分底层流错误和次生 TLS 关闭；没有将 TCP 重置伪装成正常 EOF。

手机准备带走时已停止轮询、结束应用及电脑助手，并退出到主屏幕。原 VM 配对资料和实验密钥保留；没有要求用户重新配对或操作登录。测试 JSON 只保存在忽略目录，文档不包含手机序列号、密钥或原始截图。

## 使用与回退

原电脑助手和 VM 中继无需重装。手机先启动 BLE 传输和轮询，电脑助手连上后应自动继续。VM 休眠或中继关闭仍可能显示实际连接错误；恢复后会按上述退避重试，必要时可手动重新启动轮询。

结束测试时先停止手机轮询及全部 BLE，再关闭电脑助手。回退本阶段运行方式可停用 BandKey，继续使用 VM 原系统密码登录；本阶段没有修改 VM 或宿主机登录组件。手机仍保持与手环的原配对。

用户已授权功能完善后直接安装真实主机。该条件目前尚未满足：需先收敛上述传输故障，再验证宿主机账户认证和卸载／恢复路径。当前真实主机继续只运行通信助手，实验 Provider 仍限制在 VM。
