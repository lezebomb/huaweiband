## 返回页面后 SSL 失败：电脑端修复版

2026-10-19 用户实测按 Home 后未立即看到断开，但返回后确认按钮灰色，轮询报 SSLHandshakeException。助手直连 VM 的 TLS 握手成功，证书与手机已导入指纹一致；手机后台服务仍在运行，但显示 ADVERTISING／一次断连，电脑却停在 waiting-stream／无故障／40条流。停止手机轮询、手动停止并重连电脑助手后，新数据流恢复；用户重新锁定 VM 后反馈按钮亮起且可以解锁。没有独立 WTS 观测，也未确定最初断连的唯一触发原因。

修复两处代码问题：电脑在等待新流且10秒没有通知时，每5秒尝试一次不使用缓存的 CCCD 订阅读取，单次最长5秒；确认失联后释放旧连接并走已有的最多三次重连。另将接收队列关闭中的已知 BLE 错误还原为重连分支可识别的错误，避免队列异常绕过恢复。权限拒绝及协议违规仍不自动重试；不更改 TLS 指纹、有效期或授权检查。修复版新增四项对应回归，总 Windows 79/79、核心115/115，构建零错误／警告；新版自动恢复尚未实机验证。

**最短复测：**

## 通信与信任

手机实验页 → 本机 TCP 回环 19443 → Android BandKey BLE 外围服务 → Windows BandKey 中央设备 → VM 私网端口 19443。

传递的是原有 TLS 字节流；TLS 在手机与 VM 之间终止，Windows BLE 助手不解密它。精确证书指纹、电脑签名、独立手机实验密钥、原生挑战有效期、账户/会话和一次消费仍分别验证。广播 UUID、蓝牙地址、连接成功及传输 ACK 均不授予解锁权限。没有调用蓝牙配对/解除配对 API。

手机只广播自定义服务 UUID，不广播设备名或账户标识。Windows 只查询该服务和两个特征，不探测手环。发现相同服务的冒充者可能干扰可用性，TLS 和签名仍用于阻止其授权；此实现没有将广播识别当作可信设备登记。

## 手机到 VM 使用步骤

1. 按 [VM 手机实验教程](vm-phone-bridge-test.md)登记手机实验公钥、VM 密码保管和中继。保持系统原有登录选项及可恢复快照。宿主机不安装 Provider。
2. VM 中继监听来宾的私网 IPv4、端口 19443；宿主机必须能访问它。手机配对 JSON 的 endpoint 使用 `https://127.0.0.1:19443`，保留实际 VM 的电脑 ID、公钥和证书指纹。无需 VMware NAT 入站映射。
3. 手机已有相同 APK 时直接复用，不重复安装。在 VM 实验页导入并核对配对资料，授予附近设备中的 CONNECT / ADVERTISE 权限。点击“启动前台 BLE 传输”。授权弹窗关闭后若未启动，应再次点击该按钮。
4. Windows 托盘菜单选择“手机 BLE 通信实验”，或运行 `BandKey.exe --ble-bridge`。输入 VM 私网 IP，点击连接。确认订阅完成；窗口显示阶段、MTU、流数量和字节计数。默认最长 30 分钟，可设 1–120 分钟；关闭会取消并释放连接。
5. 手机点击启动轮询，保持本页前台。手动锁定 VM；收到经过核验的请求后点击本次确认，观察 VM 是否实际返回桌面。客户端“已交付”不等于 Windows 已解锁。
6. 补测不确认、错误证书/签名、拒绝、超过 30 秒、断开蓝牙、撤权与重新锁定。每次确认只应消费一次。最后恢复普通登录、移除实验组件或按快照回滚。

手机离开页面即关闭 BLE 服务、广播和当前 TCP 连接；返回后需手动重新启动。该版不声称 ColorOS 长期后台可用。Windows 助手现对可用性故障最多重连三次，分别等待 11／12／14 秒，为 v1 手机最长 8 秒的旧 READY 等待及系统 GATT 释放留出时间。每次销毁旧订阅、队列和 TCP，再创建新连接，不延长总运行时限或授权有效期；停止可中断等待。错误帧、会话／顺序违规和权限拒绝立即终止，不自动重试，也不重发应用授权。手机关闭蓝牙、撤回权限及适配器移除仍须硬件补测。

命令行助手仅连接 RFC1918 私网或回环目标，端口固定为 19443：

```powershell
BandKey.exe --ble-tunnel --target <VM私网IPv4> --seconds 1800 --output <绝对路径.json>
```

可提供 `--ready <文件>` 和 `--stop-file <文件>` 做开发编排；停止文件应使用本轮独立路径。重连和最终停止会移除 readiness 文件，不能沿用首次连接的旧就绪状态。最终报告记录尝试次数及全部失败；`passed=true` 只表示按要求正常结束，仍须检查 `failures`，不能用它证明全程没有故障。日志包含固定错误码、异常类型、数值 HResult／Socket 错误及 EOF／字节计数，不记录 MAC、载荷、nonce、密钥或 Windows 凭据。普通代理认证后端保持不可用。

## v1 帧格式与限制

服务 UUID：`ab7c1101-5d18-4e0b-9aba-30ad640be001`；电脑写 RX `...1102...`，手机通过 TX `...1103...` 通知。TX 使用标准 CCCD。单个 GATT 中央设备和单个 TCP 流，ATT 写入须有响应；通知通过完成回调串行发送。

| 字段 | 长度 | 定义 |
|---|---:|---|
| kind | 1 | OPEN=1、READY=2、DATA=3、EOF=4、ABORT=5 |
| session | 8 | 非零随机 64 位值，小端；连接各自生成 |
| sequence | 4 | 小端，从 0 递增；小于 65536 |
| payload | 0–160 | DATA 必须非空，控制帧必须为空 |

OPEN / READY 为各方向序号 0，其后只接受 DATA / EOF / ABORT。拒绝跨会话、重复、乱序、错误长度、未知类型及结束后的任何帧。每方向最多 131072 字节，每条流最长 45 秒，电脑 TCP 建连最多 3 秒；队列最多 128 帧。最小 MTU23 可传 7 字节载荷，更大 MTU 按实际值扩展至最多 160 字节。低 MTU 下性能是否满足 30 秒授权窗口尚待实测。

Android 另用独立计时器关闭超时 Socket，避免只设置读超时却让写入永久阻塞。Windows 复用同一个 `BleStreamForwarder` 执行真实 GATT 与模拟测试，取消会中止两个方向。断线/乱序/超额失败不会延长原生挑战有效期；蓝牙 ACK 不等于应用消息已验签或系统已登录。

## 流错误排查与故障恢复入口

最早实际 VM 报告只有 `IOException`，无法补推唯一根因。新增固定诊断后分别实际捕获 VM TCP 建连超时、`target-half-close / 10054` 和 `target-read / 10053`。修复双 EOF 后重复调用 Shutdown 的结束竞态，并在双向任务取消前保留首个故障，防止把次生取消当作根因。未完整结束的真实 TCP 重置仍然失败，不伪装成 EOF。

修复后的较长轮询完成 100 条流，仍有一次 `target-read / 10053`（手机 EOF=true、目标 EOF=false），该失败保留，不能把重连策略称为消除了所有底层中止。首次人为断路只重建了 GATT、没有恢复新流；随后发现 VM 自身不可达，不能独立将失败归因于旧的 1 秒等待。代码显示 v1 手机旧 READY 等待最长 8 秒，因此加入清理等待，并用不依赖 VM 的隔离服务重新验证。

```powershell
# 显式硬件实验；手机先启动 BLE，PC 就绪后在原实验页启动轮询。
# 仅中断本测试自己的宿主机回环转发器，不改 VM、NAT 或防火墙。
BandKey.Windows.Tests.exe --phone-ble-recovery --target <VM私网IPv4> --root <本轮独立目录>
```

测试先完成至少 6 条流，关闭自己的透明 TCP 转发器直至观察到失败，再重启转发器，要求自动重连后完成至少 8 条新流。三分钟总时限，记录所有失败并正常清理；不生成确认，不解密 TLS，不独立观察恢复后的应用响应或 Windows 解锁。报告保存实际加载的 Windows DLL SHA-256；发布清单只接受与分发 DLL 完全匹配的恢复结果，不能把普通构建的不同哈希沿用到发布包。Windows 释放所有 GATT 引用后由系统异步断开的行为依据 [Microsoft GATT 客户端文档](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/gatt-client)。

2026-10-19 隔离复验通过：Mate60 原 APK、实际 GATT、MTU 517；断路前 6 条流且无基线故障，唯一一次预期 `target-connect / 10061` 后使用第二次连接完成 8 条新流，总计 14 条，主机发送 7234／接收 16544 字节。不是两端计数比对。实际加载 DLL 与发布包完全一致。USB 无数据映射，合成服务无授权请求、交付为 0；未操作 VM 或测试真实解锁。临时测试电脑资料已核对并恢复原 VM ID／证书／地址，轮询／BLE／服务均停止，屏幕常亮原值已恢复，APK 未重装。这是有限的物理传输恢复验收，长期后台、来宾睡眠与反复 TCP 中止仍待验证。
