# 返回后没有通知：0.9.5

## 本轮现场证据

2026-10-30 用户反馈白天可用、下午再次断开。电脑仍是昨晚的常驻进程，监护与报告正常推进，手机签名状态和 BLE 当时也已恢复；不能沿用昨天“进程卡住”的结论。手机自身退出记录显示当天 18:18 被系统以 `OTHER KILLS BY SYSTEM / o-kill` 清理，早些时候也有系统清理记录。当前进程存活不代表外出期间一直运行。

发现并修复了一个可复现的软件缺陷：固定手机通道在上一条通知仍有效时，停止附带独立签名的 Windows 请求轮询；新锁屏的直接挑战没有改变刷新计数，因此可被旧的两分钟通知遮住。另发现设备查询缺少回调超时，一次未返回的 SDK 调用可令后续查询永久停止。本轮没有取得完整故障时段的连续追踪，不能断言这些是所有真实失败的唯一原因。

## 修改

- 在原有三秒状态上报中继续附带独立签名轮询，不另开高频 HTTPS 请求。返回的新挑战可替换尚未过期的旧通知；相同挑战保留原期限并只发送一次。已排队的决定仍先处理，旧回调不能批准新请求。
- 手环连接查询五秒超时后报告未知并重新查询；通过查询代次拒绝迟到或重复回调。未知不能当作离开、接近或授权。
- 手机收到系统蓝牙连接事件后，可恢复用户已启用、已允许后台运行的本应用服务，保留原周期任务兜底。不读取蓝牙设备地址／名称，不依此判断距离或解锁；明确停止仍被尊重。
- 实际中继恢复测试复现了三秒 I/O 超时：电脑已生成新请求，手机却连续读超时。将固定通道的连接／读取上限改为八秒，给新 TLS 连接及上一条流收尾留出余量。这是等待上限，不是新增固定延迟；已消费的批准决定仍不重试。
- 本地诊断增加手环通知阶段和设备查询超时计数，区分有效请求、SDK 接受和实际显示。
- 手机最终更新为 0.9.5/code22；code21 是先行复现该超时的本地候选，不计为完成部署。电脑监护、原生认证、两分钟期限、关闭自动锁屏、原系统登录方式、手机密钥和手环配对不变。

Android 官方将 [ACL_CONNECTED 列为可在清单中接收的广播例外](https://developer.android.com/develop/background-work/background-tasks/broadcasts/broadcast-exceptions)，[关闭电池优化属于后台启动前台服务的例外](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)。连接广播只是额外恢复机会，不能保证厂商系统不清理进程，也不能保证每次携带手机返回都会产生该事件；不是将周期任务伪装成秒级保活。

## 构建与验证边界

Java 生产逻辑 151 项检查通过，包含新锁屏替换未过期通知、重复上报不延长期限、排队决定不被轮询抢先、六十秒后确认的模拟时间检查，以及查询超时／迟到回调。Android 最终构建成功，Lint 零错误、六项原有警告。APK 签名证书与原应用一致；两次保留数据覆盖更新分别用于原缺陷修复和实测发现的超时修正，手机公钥仍为原登记指纹。

实机中仅暂停 BandKey 电脑通道二十秒，恢复时观察到新原生挑战及上述三秒读超时，才增加八秒 I/O 余量。最终更新后，另仅以本应用 UID 结束一次手机进程：Android 约 2.3 秒自动重建服务，未手动运行恢复任务；随后 BLE 和签名状态自动恢复。约两分钟的十二次后台采样全部保持连接与新鲜签名状态，期间新增三十五次 HTTP 完成、零新增失败。系统清理与此次自有 UID 结束并非相同退出原因，不能由后者保证所有 OEM 清理都能以相同速度恢复。

最终观察时电脑已经处于未锁屏状态，因此没有主动再锁用户电脑。旧通知替换及期限通过软件检查，新锁屏通知的真实显示／手环点击解锁仍待用户可操作时复验。用户本轮无法操作手环，不把 SDK 接受发送或软件模拟当作手环实际显示、点击解锁或长期稳定性验收。没有自动批准任何主机认证。

## 恢复

本地 `maintenance/Current/BandKey-bridge-0.9.5.apk` 为本轮安装包，原 0.9.4 APK 保留在 `maintenance/Rollback/Phone-0.9.4`。原签名密钥备份保持私有。需要回退时优先使用原源码和原签名生成更高版本号的回退包覆盖，不卸载、清数据或强行更换手机密钥。SDK、JDK、Gradle 和生成产物完成后清理，不是运行依赖。
