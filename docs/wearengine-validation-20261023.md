# Wear Engine 真实手环接入（2026-10-23）

本轮在一加 Android 16 上使用官方 Wear Engine 5.0.3.304，保留 Band 11 Pro 的现有配对。Mate60 最初连接时，授权后设备查询返回错误 4（未绑定设备）；没有为继续测试而迁移或重置配对。用户随后改接一加，本轮真实手环结果均来自一加。

## 本轮修正与接入

旧代码用 `getBondedDevices()` 返回的设备对象判断通知能力，在本机实际得到 2（未知），因而会阻止发送。改用 `getCommonDevice()` 后得到支持值 0，并完成了真实通知反馈。[华为设备查询文档](https://developer.huawei.com/consumer/es/doc/connectivity-Guides/device-connection-management-0000001050779152)区分 P2P 设备列表和完整 Wear Engine 设备列表，说明能力值 0／1／2 分别代表支持／不支持／未知。

主界面新增“手环按钮测试（不会解锁电脑）”。该独立页面不创建电脑客户端或签名身份，通知标题为“BandKey 按钮测试”，内容说明仅测试。只接受所选设备本次 30 秒内的明确点击，离开页面、取消、超时后不再接受旧回调。

VM 实验页新增“使用真实手环确认”选项，默认关闭。开启后停用两个手机测试按钮，将经过电脑签名验证的当前挑战发送到所选手环。Wear Engine 回调已消费一次性票据，提交阶段只检查消费后的有效状态，不会第二次消费导致丢弃真实点击。模式切换、停止、离开页面均取消原票据。当前测试仍要求手机实验页面处于已解锁的前台。

仅通知发送成功不签名。真实手环点击后仍需检查当前请求、票据、有效期及客户端，再由手机实验 Keystore 密钥签署原生请求。电脑中继和 Provider 保持现有的验签、过期及一次性检查。这是手机持有设备密钥的桥接架构，没有声称手环自身持有 Windows 登录私钥。

## 手环到 VM 的最短联调步骤

1. 保留 BandKey-Win11 的快照与系统密码登录，仅在此隔离 VM 内运行安装器。Ubuntu 和宿主机登录组件不变。
2. 更换手机时须登记新手机的实验公钥。一加的 72 字节 `.bandkeypub` 已导出并经 CNG 公钥格式验证，准备为本机只读数据 ISO。不要把主界面的普通桥接身份与 VM 实验公钥混用。
3. 在 VM 关闭旧中继，用安装器 Remove 原实验，再选 **Install phone-confirmation VM experiment**，核对当前手机公钥并自行输入 VM 账户密码。相同手机已登记时无需每轮重装。
4. VM 中继窗口导入同一公钥，监听 VM 实际私网 IP。手机访问地址为 `https://127.0.0.1:19443`，先使用现有 USB 透明隧道，无需同一 Wi-Fi。手机导入公开配对 JSON，核对电脑 ID 和 TLS 指纹。
5. 手机 VM 实验页勾选“使用真实手环确认”，启动轮询，保持页面前台。仅锁 VM；真实手环出现请求后点确认，观察是否实际回桌面。手机显示交付签名不能替代 Windows 桌面结果。
6. 再锁 VM，先不点击并观察保持锁屏，然后在手环拒绝，也应保持锁屏。不要将本次普通通知测试的 `confirmed`／`denied` 当成 VM 解锁／拒绝的证据。

回滚时先停止手机轮询及宿主机传输助手，再停止 VM 中继。在 VM 安装器 Remove 实验，恢复系统原登录方式；必要时由用户恢复测试前快照。虚拟机键鼠操作由用户完成。

## 验证范围

本轮 Android `assembleDebug`、`lintDebug` 和 APK 签名校验通过。Lint 为 0 错误、4 警告。构建脚本的生命周期 19/19、BLE 期限 22/22、生产帧编解码 22/22 和 TLS 错误分类 5/5 均通过；这些软件测试不作为手环或 Windows 登录证据。Windows 和原生 Provider 代码未变，本轮未重复执行旧的整套 Windows 回归。

真实手环至 VM 的 USB、BLE 解锁均已有上述实机结果，VM 桌面由用户确认，未独立采集 WTS。BLE 授权数据不经过 USB 映射，USB 仅用于手机操作和记录；没有拔线独立运行验收。

BLE 本轮不能标记为持续连接稳定：工具受限进程最初在 `connect-device` 阶段失败，没有产生授权数据；改以普通宿主机权限启动后 GATT 连接成功，MTU 517，共完成 14 条流。完成解锁后，后续轮询出现 `SSLHandshakeException`，传输记录 3 次 `target-read / SocketException 10053`，均为手机先 EOF、目标未 EOF。最后停止时的 `passed=true` 只代表响应停止指令，不抵消这些故障。新增应用私有、有界 TLS 异常原因链记录以进一步定位；不关闭证书、签名或有效期检查，不自动重发授权决定。

### 0.3.1 连接诊断

诊断版在应用私有目录仅保留最后一条异常原因链，最多 8 层、每层 TLS 原因最多 512 字符。实机捕获 `SSLHandshakeException → EOFException`，两层原因为 `connection closed`；这次记录没有证书拒绝异常，仍不能据此定位唯一的关闭发起方。

随后仅轮询、不签署或交付解锁决定的对照结果如下。原始记录均在本机忽略目录，不进入 Git。

| 条件 | 结果与限制 |
|---|---|
| 原有 TLS 会话缓存，直接 BLE → VM | 10 条完整流，出现 1 次相同 `target-read / 10053`，手机记录握手关闭 |
| 临时改为每次新建 TLS 会话，直接 BLE → VM | 20 条完整流，仍出现 1 次 `target-read / 10053`；该尝试未解决问题，已撤回 |
| 临时透明 TCP 观测转发，BLE → 本机转发 → VM | 23 条完整流、1 次 GATT 连接、无传输失败；记录仅包含 TLS 记录类型、长度和 EOF 时间，不解密或保存载荷。因为路径及临时 TLS 设置都不同，这不是直接 BLE 链路修复验收 |

最终 APK 已恢复原有 TLS 会话实现，只保留错误诊断。停止轮询、传输助手及临时观测进程后，保留数据安装回最终 0.3.1，手机不继续轮询或广播；USB 无数据映射。没有改变 VM 登录组件、配对资料或账户配置。最终 APK 构建及签名校验通过；没有重新执行真实手环点击和 VM 解锁，不能把旧版整套实测标为新版通过。
