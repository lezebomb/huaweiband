# 手机常驻传输恢复：0.9.2

## 这轮故障的证据

先前的35秒通信中断测试没有收到新的手环通知，原生登录请求最终过期，没有签名交付。用户看到手机回到桌面，原因是本地测试脚本恢复服务后主动发送了 Home；检查时 BandKey 进程和前台服务仍在，常驻开关也为启用，不能将回桌面认定为应用崩溃。已移除该测试脚本的 Home 操作。

真正观察到的问题是：前台服务仍在，但 BLE／HTTPS 状态长时间没有恢复。原来仅凭“广告已启动”的本地标志无法证明电脑仍可发现和通信。日志还出现过订阅丢失和过期 GATT 句柄；不能仅凭这些结果断言唯一根因。

2026-10-28继续检查时，手机已无BandKey进程。应用自身的历史退出记录明确显示00:50发生系统清理（`OTHER KILLS BY SYSTEM`），不是Java崩溃，也不是上述Home操作。旧运行文件仍能读取，不能把该旧文件的连接标志当作当前进程仍活着。

## 修复

- 主机常驻手机模式连续45秒没有完成有效的固定证书 HTTPS 响应后，取消旧待确认请求，关闭旧的本应用 BLE／回环监听，再重建广告和 GATT 服务。这个计时只控制传输恢复，不是自动锁屏或批准解锁。
- 更换传输时保留原来的运行截止时间、显式停止状态和累计计数。旧 VM 的30分钟限制不延长。原始生命周期、一次性请求和独立 Windows 验签仍生效。
- 给新广告单独10秒启动窗口，避免旧运行已经超过10秒就立即错误终止新广告。重建失败会清理新旧资源。
- 监听器只复用本应用的本机回环端口；不切换手机全局蓝牙、不重置／重新配对手环、不修改运动健康。
- 应用私有 `wear-runtime.json` 每5秒原子保存脱敏状态，含广告／连接状态、HTTP计数与传输重建次数，不含账户、私钥、Windows密码或健康记录。以后无需反复通过手机界面导出才能判断后台状态。
- 0.9.2将本地HTTPS调用方的TCP重置／关闭限制到当前流：仍校验同一会话、序号、字节上限和截止时间，读到对端匹配EOF后才可处理下一流。不因本地`Broken pipe`直接撤销整个GATT订阅。错误帧、BLE取消、缺失EOF仍失败；不重试决定，不把截断TLS记作成功。
- 系统JobScheduler每15分钟获得一次恢复机会，只有用户先前启用常驻、没有更新的主动停止记录、且当前应用有电池优化例外时，才尝试恢复前台服务。显式停止同步保存关闭状态并撤销任务；Android任务管理器的用户停止记录同样阻止恢复，重新明确启用后才恢复。任务由系统签名权限保护，不增加精确闹钟、保活音频或其他应用权限。
- Windows重连改为无缓存枚举主服务后选取BandKey自身UUID；其他服务立即释放，不读取其特征。GATT写入、连接和取消订阅的托管等待受已有期限独立约束，避免底层取消延后时阻塞清理。已打开却超过10秒没有收到数据的流也进行有界CCCD健康检查，避免手机进程消失后仍等满45秒流期限。错误帧及权限失败的终止规则不变。

0.9.1及后续0.9.2均保留数据更新到当前一加，APK原签名和手机公钥保持一致；未卸载。0.9.2另恢复了仅BandKey的电池优化例外。Windows仅更新用户态常驻代理，原生登录组件哈希核对未变，离开自动锁屏仍关闭。

## 验证

0.9.2 Java共136项通过，其中后台租期／资源检查30项，覆盖关闭旧资源再创建新资源、计数不回退、截止时间不延长、显式停止、重建失败清理、新广告启动窗口、单调时钟与进度计数回退。新增4项真实本地TCP套接字检查覆盖重置后排空至EOF、半关闭保留响应、排空时拒绝错误会话及租期取消；这些不是真实BLE硬件测试。另增加5项用户停止与重新启用的恢复门控检查。Android编译和Lint通过，0错误、6项警告；新增2项为主动使用同步偏好写入，以便停止／明确启用先持久保存再调度。其余4项与原版相同，未放宽固定证书校验。

0.9.1实际手机与主机桌面验证：暂时停止电脑端BandKey，手机自身检测到通信无进展后重建1次传输；电脑端恢复约13秒后取得新鲜状态。HTTPS完成计数由68增至72，随后继续增长。测试不锁Windows，未操作手环配对，自动锁屏保持关闭。这是实际BLE／HTTPS恢复结果，不是Windows解锁结果，也不是物理携带离开／返回验收。

0.9.2启动后，真实BLE通道恢复，主机收到新鲜的有效签名状态，手机先完成9个固定证书HTTPS响应且故障0。进程恢复与后续持续通信结果另记；不能把“任务已登记”算作厂商整夜保活通过。

进程中断测试：仅终止本应用进程，并强制调度本应用恢复任务；不强行停止应用、不关闭全局蓝牙。第一轮在85秒观察期限内未恢复，随后才观察到有效通信，因此该轮未记为通过。加入Windows重新发现与等待期限修复后，第二轮48.2秒恢复有效HTTPS响应，手机传输无需重建，随后15个响应／故障0，主机收到新鲜签名状态并记录一次通信返回。这个结果不是通知延迟；系统自身的sticky恢复与任务可能都参与，不能据此单独归因于JobScheduler，也不能当作自然15分钟调度或整夜后台验收。

最后加入静默活动流健康探测后，同一故障复验31.9秒恢复有效HTTPS及主机新鲜签名状态，手机传输重建0次；Windows记录旧连接健康检查失败后成功建立第2次连接。此轮无新解锁决定，电脑始终保持桌面。上述时间均为单轮故障恢复观测，不是正常通知速度或上限承诺。本地TCP排空修复在Java真实套接字检查通过，本轮未发生`localSocketAborts`，不把它另算作真实BLE故障分支已触发。

Windows构建0错误／0警告，101项检查通过（首次运行因当前shell缺少`javac`路径有1项环境失败，补齐本地JDK路径后全数通过）。检查未注册登录组件，未调用本机锁屏或提交本机Windows登录。

后续整轮受控中断已通过“锁屏→手机进程中断→旧挑战过期→通信恢复→新手环通知→确认→Windows认证成功及桌面恢复”，见[11:14实机记录](host-return-unlock-20261028.md)。实际携带手机返回、自然恢复任务调度及长期厂商后台策略仍待验证，不从受控测试继承。

Android恢复任务按系统调度执行，不能承诺精确15分钟或立即复活；用户强行停止、撤销权限或厂商额外限制时，仍可能需要手动重新启用。参考[后台启动前台服务的限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)、[用户停止前台应用](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping)、[JobScheduler周期与持久化](https://developer.android.com/reference/android/app/job/JobInfo.Builder)。

## 回退

若有明确回归，保留现有配置、公钥与系统登录方式，用原签名0.9.0 APK进行允许降版本的覆盖安装，不要卸载应用以免删除Keystore身份。回退后保留原来的Windows密码／Hello入口。应用源码与固定SDK可由仓库恢复；原签名APK和运行记录仅保存在本机忽略的构建目录。

Windows代理可从本机保留的上一完整Host包恢复：先通过托盘退出当前BandKey，在旧包执行`install-host-agent.ps1`，再保持自动锁屏关闭。这个脚本仅替换当前用户代理，不运行HostSetup，不重新登记密码或替换登录组件。本阶段始终保留独立原生恢复入口与Windows系统登录方式。
