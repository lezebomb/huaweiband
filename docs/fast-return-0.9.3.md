# 返回通知延迟优化：0.9.3候选

目标是用户携带手机和手环返回后，5秒内看到新的确认通知。**0.9.3及配套主机用户态代理已保留数据部署，但本轮实际返回没有新通知，5秒目标未通过。** 直接锁屏仍有通知；后续电脑端关闭会话修复已完成软件检查，尚未部署或实机验收，见[故障与候选](return-reconnect-fix-20261028.md)。原生登录组件未更换，自动锁屏继续关闭。

## 已验证的真实返回基线

2026-10-28用户将手机从USB拔下，手机和手环一起离开，再返回；手机已在主屏幕并熄屏，未重新打开BandKey。电脑只被用户手动锁定，观察脚本不暂停通信、不锁电脑、不改变配对。

主机在11:20:43记录签名状态失去新鲜性，11:22:30恢复新鲜签名状态；随后新挑战被真实手环批准，原生记录`approval-verified`、`grant-consumed`和`Windows-result | 0x00000000`，WTS也记录解锁。用户确认新通知点击后回桌面，同时反馈返回后通知约20秒。

这一轮还跨过主机25分钟会话轮换，旧会话被撤销，新会话计数重新开始。因此不能用轮换后归零的“通信返回次数”否定已观察到的中断／恢复。0.9.2没有完整的SDK投递起点计时，无法精确分摊用户感受到的20秒，也不能把某一等待直接认定为全部根因。

## 候选修改

- 主机只对可恢复的连接故障缩短等待：同一轮250／500／1000毫秒，耗尽该轮后的重新开始等待500毫秒。错误帧、权限故障的分类不变，不重试应用层授权。旧VM的保守等待仍保留。
- 手机区分真实GATT连接代次。连接或CCCD改变后，旧READY等待会及时退出；旧工作线程不能再取消或继续发送到新代次。新连接不会继承旧CCCD就绪状态或旧HTTP退避计时。
- 重连、连接状态变化和恢复性HTTP失败后，最多5秒短窗口快速追赶状态／原生请求；主机模式的失败退避从250毫秒增至最多2秒。稳定时仍每3秒上报，不永久提高上报频率；所有调用仍串行并受服务器限流约束。
- 主机手机服务的空闲调度间隔改为200毫秒，VM仍为500毫秒。不减少接近稳定等待、不延长挑战期限、不绕过固定证书、状态签名、原生独立验签或真实手环点击。
- 增加从实际CCCD就绪到验证新请求、到Wear Engine SDK接受通知的分段计时。SDK接受不是手环已经显示，也不能当作Windows已解锁。

## 软件验证及剩余工作

Java139项通过，包含真实本地套接字关闭、旧代次READY及时取消、重连退避重置不能复用已消费批准。Windows102项通过，新增生产快速重试策略下先清理旧资源、再建立新连接，遇权限失败仍终止，并保留原期限。Windows构建0错误／0警告；Android构建及Lint通过（0错误、6项既有警告）。这些结果不代表真实蓝牙或手环显示已达到5秒。

部署已按“手机原签名保留数据更新0.9.3→主机用户态代理”顺序完成。核对手机公钥保持一致、主机原生组件哈希未变；不运行原生安装器，不重新登记Windows密码，不更新VM。该顺序确保主机快速重试配合新版手机的旧READY取消机制。之后测量真实携带返回到通知显示，结合分段计时判定5秒目标；未达标继续定位，不写成已通过。

部署前另查到，手机11:55被一加系统以`OTHER KILLS BY SYSTEM`清理，恢复任务也已不在，但常驻偏好仍开启。实际UI核对：“完全允许后台行为”已开，独立“自启动”开关未开。现仅为BandKey开启“设置→应用→自启动”，重新启用常驻后恢复任务显示就绪。该修正不代表已通过整夜后台验收，也没有关闭系统省电或其他应用的安全限制。

候选APK、完整主机包、原签名校验和本机候选清单在忽略的`artifacts`中。手机带走期间未操控或更新；重新连接后只覆盖安装新版一次，没有卸载或重复安装。需要回退时，用原签名0.9.2覆盖恢复手机、恢复上一完整主机代理包；不要卸载手机应用或改动原生登录组件。自动锁屏继续关闭。
