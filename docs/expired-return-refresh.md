# 两分钟后的返回与刷新恢复

用户反馈：锁屏后立即有通知，携带手机与手环离开超过两分钟，回来却没有新通知。本轮用户不能参与手环测试，因此使用合成账户／时钟和真实 HTTPS、文件 API 检查故障路径，不将这些检查计作实际返回验收。

## 两种期限

手环确认对应的 WIN 挑战为 **120 秒**。过期后返回，需要先交换一个独立的 NEW 刷新证明，让 Windows 创建全新的 WIN 挑战。NEW 只有 **10 秒**有效，并不能用于登录。

此前在创建 NEW 后就把本次返回标为已处理。如果响应丢失、证明到期或原生组件没有及时生成新挑战，标记一直保留，后续有效状态上报也不再创建刷新请求。另一个问题是未被原生组件消费的过期 `request-renewal.bin` 会阻止后续刷新文件落地。

这两个缺陷由软件检查复现，不足以证明它们覆盖每次硬件返回失败的全部原因。出门未真正中断通信、手机系统清理及手环投递仍属于独立问题。

## 修复边界

- 主机收到新鲜的有效签名状态、确认仍锁屏且已稳定接近时，丢失／未完成的 NEW 到期后可以重新创建，使用新随机数与新签名。同一次返回最多恢复三次；真正的新返回或锁屏会话重新建立其状态。
- 只恢复尚未观察到新 WIN 的刷新阶段。一旦已有 WIN，不会因为它到期、被拒绝或尚未点击而自动续期或不断弹通知。两分钟期限不延长，已消费的解锁决定不重发。
- 重复交付同一份当前 NEW 文件为幂等操作。只允许替换结构有效、同一账户／会话且已经过期的刷新文件；另一份有效证明、畸形条目、重解析点和不同账户／会话文件保持。写入通过临时文件和原子移动完成，原生签名／期限验证独立保留。
- 报告增加 `renewalRecoveries`，用于区分普通返回与刷新恢复。没有恢复自动锁屏，也没有更换手机密钥或改变手环配对。

## 验证与部署

修复前，新增五个核心回归中的三个失败；修复后核心 **190/190** 通过。Windows 构建零错误／警告，集成 **107/108** 通过：唯一未通过项是找不到 `javac` 的既有 Java 互通检查，本轮没有修改 Java 协议，不为此恢复 Android/JDK 工具链。

新增 HTTPS／文件检查涵盖：两分钟后返回且原生未消费刷新文件、刷新恢复后旧确认拒绝、同一证明重复交付、保留另一份仍有效的证明、只替换已过期且匹配上下文的文件、畸形或外账户／会话文件保持。所有账户均为合成输入，没有调用真实 Windows 登录认证。

仅更新当前电脑后台的 `BandKey.dll`、`BandKey.Core.dll` 及对应 PDB；WinRT 运行依赖哈希一致。原生登录 DLL、原密码／Hello、手机应用与配对不变。后台原暂停／自动锁屏设置恢复后，由原登录任务重新启动。真实携带返回和手环点击本轮未验证。

## 回滚与本地文件

当前补丁在 `maintenance/Current/ReturnRefresh`，更新前四文件备份在 `maintenance/Rollback/ReturnRefresh`。退出整个后台进程后，将备份四文件复制回 `%LOCALAPPDATA%\Programs\BandKeyHostPilot`，再运行原 `BandKeyHostPilot-<SID>` 登录任务即可；不要为此重新安装登录组件或重新登记密码。

本地保留小体积补丁、回滚包和私有验证收据。临时 .NET SDK 与生成缓存清理后，已安装程序仍独立运行。源码、必要测试与构建入口同步 GitHub。
